# Test 1 — 질문 계획과 사전 예측

> 실행 **전에** 적은 문서다. 질문·의도·예측은 결과를 보고 고치지 않는다.
> 결과는 별도 문서(`test_1_result.md`)에 남기고, 이 문서의 예측과 대조한다.

- 작성일: 2026-11-28
- 관련: 이슈 #29, [ADR-0004](../../adr/0004-judge-answerability-in-backend.md), PR #34 · #38, [엣지 케이스](../../nl2sql-edge-cases.md)

## 1. 목적

1. **판정 정확도** — Jev 판정이 `judge-criteria.yml` 기준대로 나오는가. 특히 **오거절**(답할 수 있는 질문을 거절)이 생기는가.
2. **화면 매핑** — 거절·실패가 errorCode 별로 맞는 카드(안내 / 다시 입력 / 오류)로 보이는가.
3. **통과 경로** — 거절되지 않은 질문이 SQL 생성·실행까지 가서 어떤 결과(정상 / 0행 / 100행 잘림 / 실패)를 내는가.

## 2. 가설

| ID | 가설 | 확인 질문 |
|---|---|---|
| H1 | PC 와 무관한 질문은 `out_of_scope` 로 거절된다 | Q01–Q07 |
| H2 | "이 DB 에 없는 것" 목록의 데이터를 요구하면 `missing_data` 로 거절된다 | Q08–Q14 |
| H3 | 조회 대상이나 기준이 빠진 질문은 `ambiguous` 로 거절된다 | Q15–Q20 |
| H4 | 스키마 안에서 끝나는 질문은 표현이 거칠거나 조건이 적어도 거절되지 않는다 (오거절 0) | Q21–Q32, Q39–Q41 |
| H5 | 견적 조합 요청은 `recommendation` 으로 판정되지만 거절되지 않고 견적 생성으로 넘어간다 (PR #38) | Q33–Q38 |
| H6 | 판정을 통과한 위험·과부하 질문은 생성 또는 실행 단계에서 막히고, 데이터가 새지 않는다 | Q45–Q48 |

## 3. 실험 환경

| 항목 | 값 |
|---|---|
| 브랜치 / 커밋 | `feat/#29-frontend-error-card` / `cec7a53` (PR #38 머지 포함, vectordb 재생성 `d2dadd0` 포함) |
| 커밋 전 변경 | `Nl2SqlService` 에 실험 기록용 로그 추가 (생성·실행 시간, 생성 시도 횟수, 실패한 SQL). 동작은 같다 |
| 판정 모델 | TypeSafe `jev-1.14.0` |
| 판정 기준 | `classpath:nl2sql/judge-criteria.yml` (recommendation 은 거절 대상 아님) |
| 스키마 요약 | `classpath:nl2sql/schema-summary.txt` |
| **거절 임계값** | **0.7** (실행 중인 컨테이너 기준) |
| 판정 타임아웃 | connect 1s / read 3s. 실패 시 fail-open(거절 없이 진행) |
| SQL 생성 | nl2sql (LangGraph), Groq `openai/gpt-oss-120b`, 재시도 최대 3회 |
| 검색 | Chroma + `BAAI/bge-m3` (`nl2sql/vectordb`, git 추적본) |
| 실행 제한 | 최대 100행, 쿼리 타임아웃 10초, 읽기 전용 트랜잭션 |
| 화면 | `localhost:3000` (2026-11-28 17:02 빌드, 오류 카드 적용) |

> ⚠️ 임계값 주의: 로컬 `application.yml` 은 기본값을 `1.1`(거절 안 함)로 바꿔 두었지만,
> `docker-compose.yml` 이 `TYPESAFE_CONFIDENCE_THRESHOLD` 를 `0.7` 로 넣어 덮어쓴다.
> 이 실험은 **0.7 로 거절이 일어나는 조건**이다. 거절을 끈 채로 판정만 보려면 `.env` 에
> `TYPESAFE_CONFIDENCE_THRESHOLD=1.1` 을 넣고 백엔드를 다시 띄운다(그건 별도 실험으로 기록).

### 거절 규칙 (예측의 근거)

```
verdict ∈ {answerable, recommendation}         → 진행
verdict ∈ {out_of_scope, missing_data, ambiguous}
    confidence ≥ 0.7                           → 422 거절 (NL2SQL_<VERDICT>)
    confidence < 0.7                           → 진행
판정 실패 · 타임아웃                             → 진행 (fail-open)
```

## 4. 진행 방법 (자동 실행)

질문은 [`tools/nl2sql_eval.py`](../../../tools/nl2sql_eval.py) 로 백엔드에 직접 보낸다.
질문 목록과 예측은 이 문서와 같은 내용을 [`test_1_questions.json`](test_1_questions.json) 에 기계가 읽는 형태로 둔다.

```bash
# 저장소 루트에서. 도커 4개 서비스가 떠 있어야 한다.
python tools/nl2sql_eval.py "docs/test/test 1/test_1_questions.json"
```

- 질문은 순서대로 하나씩 보내고, 사이에 3초 쉰다(`--delay`). 50개 기준 수 분~십수 분 걸린다.
- 실행 전에 백엔드 health, nl2sql 실행 여부, TypeSafe 키를 확인하고 하나라도 없으면 멈춘다.
- **실행 중에는 같은 백엔드로 다른 질문을 보내지 않는다.** 질문별 로그를 시간 구간으로 잘라 붙이기 때문에 섞인다.
- 중간에 끊겨도 끝난 질문까지는 `results.jsonl` 에 남는다. 남은 질문만 `--only Q21,Q22,…` 로 이어서 돌릴 수 있다.
- 간편 입력 질문(Q33–Q35)은 프론트가 보내는 것과 같은 `programs`·`budgetMin`·`budgetMax` 를 함께 보낸다.
  나머지는 질문 문장만 보낸다(= 간편 입력을 비우고 "추가 요청사항"에만 쓴 것과 같다).

### 결과 위치

`docs/test/test 1/runs/<실행 시각>/`

| 파일 | 내용 |
|---|---|
| `meta.json` | 실행 조건: 브랜치·커밋·커밋 안 된 변경, 컨테이너의 임계값, 판정 모델, SQL 생성 LLM, 이미지 생성 시각, 기준·스키마·few-shot·vectordb 파일 해시 |
| `results.jsonl` | 질문별 전체 기록: 요청, HTTP·code·message, 판정·확신도·판정 지연·거절 여부, SQL, 컬럼, 행 수, 결과 5행, 생성 실패 사유·재시도 횟수, 실행 실패 예외, 해당 구간 백엔드 로그 원문 |
| `results.csv` | 스프레드시트용 요약 (엑셀에서 한글이 깨지지 않게 BOM 포함) |
| `report.md` | 지표 요약, 결과·판정 분포, 질문별 표, 질문별 상세(SQL·오류·결과 일부) |

보고서만 다시 만들 때: `python tools/nl2sql_eval.py --report-only "docs/test/test 1/runs/<실행 시각>"`

### 실험용 백엔드 로그

`Nl2SqlService` 가 아래 로그를 남기고, 실행기가 이를 읽어 질문별로 붙인다.

| 로그 | 언제 | 담는 것 |
|---|---|---|
| `판정 결과 verdict=… confidence=… model=… latency=…ms` | 판정 받음 | Jev 판정 |
| `판정으로 거절했습니다. verdict=… confidence=… question=…` | 거절 | |
| `SQL 생성 완료 retry_count=… latency=…ms sql=…` | 생성 성공 | 생성 시간, 시도 횟수, SQL |
| `SQL 생성 실패 (retry_count=… latency=…ms): …` + `생성에 실패한 마지막 SQL: …` | 생성 실패 | 실패 사유, 마지막으로 시도한 SQL |
| `SQL 실행 완료 rows=… latency=…ms` | 실행 성공 | 실행 시간, 행 수 |
| `생성된 SQL 실행 실패 (latency=…ms): …` + 예외 | 실행 실패 | 실행 시간, SQL, 예외 |

> `retry_count` 는 이름과 달리 **생성 시도 횟수**다. `query_generator` 가 호출될 때마다 1 씩 올리므로
> 첫 시도에 성공해도 1 이다(최대 3). 보고서에는 "생성 시도"로 적는다.

총 응답 시간 = 판정 + 생성 + 실행 + 그 밖의 오버헤드(HTTP, 트랜잭션 등).

### 화면 이름 (예측 표에서 쓰는 말)

| 화면 | 언제 |
|---|---|
| 안내·금지 / 안내·DB / 안내·물음표 | 422 `NL2SQL_OUT_OF_SCOPE` / `MISSING_DATA` / `AMBIGUOUS` |
| 주황·다시 표현 | 422 `NL2SQL_GENERATION_FAILED` |
| 주황·입력 확인 | 400 `INVALID_INPUT` · `INVALID_TYPE` |
| 빨강·조회 실패 | 422 `NL2SQL_EXECUTION_FAILED` |
| 결과 표 | 200, `N개 결과` |
| 0행 | 200, `조건에 맞는 부품이 없습니다.` |

## 7. 평가 지표

결과 문서에서 아래를 계산한다.

- **판정 정확도**: 예상 판정과 실제 판정이 같은 비율. 전체 / F 그룹 제외 두 가지로 본다.
- **오거절 수**: 예상이 answerable · recommendation 인데 422 로 거절된 질문 수. ADR-0004 기준 가장 큰 위험이므로 **목표는 0건**.
- **놓친 거절 수**: 예상이 거절인데 통과한 질문 수. 확신도가 0.7 바로 아래였는지 함께 본다.
- **화면 일치율**: 실제 code 에 대해 의도한 카드가 떴는지.
- **보안**: Q45 · Q46 에서 데이터 노출·변경이 없었는지 (예외 없이 통과해야 함).
- **지연**: 판정 latency 평균·최대 (read-timeout 3s 대비).
