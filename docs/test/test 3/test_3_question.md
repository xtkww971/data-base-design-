> 실행 **전에** 적은 문서다. 질문·채점 기준·예측은 결과를 보고 고치지 않는다.

- 작성일: 2026-11-28
- 이전 실험: [Test 1](../test%201/test_1_question.md) · [Test 2](../test%202/test_2_question.md)
- 질문 파일: [`test_3_questions.json`](test_3_questions.json) (41개 = 품질 31 + 회귀·보안 10)

## 1. 목적

1·2차는 LLM 하루 토큰 한도에 걸려 **판정은 거의 다 봤지만 SQL 품질은 거의 못 봤다**
(유효한 통과 결과 1차 12건, 2차 4건). 3차는 **통과해야 하는 질문의 SQL 이 맞는지**를 본다.

- "통과했다(200)"가 아니라 "**맞는 결과를 냈다**"를 센다.
- 판정 회귀(Q02·Q19 의 확신도 흔들림, Q17 오판정)와 보안(Q45·Q46)은 적은 수로 함께 확인한다.

## 2. 채점 방법

실행기(`tools/nl2sql_eval.py`)가 통과한 질문마다 세 가지를 본다. 형식은 실행기의 "쿼리 품질 채점" 주석에 있다.

| 기준 | 내용 | 예 |
|---|---|---|
| **SQL 규칙** (`sql_checks.must / must_any / must_not`) | 질문의 조건이 SQL 에 들어갔는가. 정규식, 대소문자 무시 | Q21: `price <= 500000`, `memory_capacity DESC` |
| **행 수** (`sql_checks.rows`) | 결과 행 수가 맞는가 | Q26: `eq:3`, Q32: `zero` (`builds` 가 비어 있음) |
| **정답 결과** (`gold`) | 사람이 쓴 기준 SQL 을 같은 DB 에서 돌려, 결과 키(module_id 등) 집합을 비교 | Q28: 정답 22행 |

- `gold.match = set`: 결과 키 집합 = 정답 집합이어야 일치. `subset`: 결과 ⊆ 정답이면 일치(LIMIT·동점·100행 잘림이 있는 질문).
- 정밀도 = 맞게 나온 키 / 나온 키, 재현율 = 맞게 나온 키 / 정답 키.
- 기준 SQL 검증: `python tools/nl2sql_eval.py "docs/test/test 3/test_3_questions.json" --check-gold` (질문은 보내지 않는다).

### 채점에 영향을 주는 DB 값 (2026-11-28 확인)

| 값 | 저장 형태 | 위험 |
|---|---|---|
| 모니터 해상도 | `4K UHD (3840x2160)`, `QHD (2560x1440)` … | `resolution = '3840x2160'` 처럼 쓰면 0행 |
| 파워 인증 | `80PLUS PLATINUM` … | `= 'PLATINUM'` 이면 0행 |
| SSD 폼팩터 | `M.2 2280`, `2.5인치` | `= 'M.2'` 이면 0행 |
| `builds` | **0행** | Q32 의 정답은 0행 |
| `performance_score` | 1200개 중 150개 NULL (그래픽카드는 NULL 없음) | |
| SSD 쓰기 속도 최댓값 | 14000 이 6개 (동점) | Q26 은 이 6개 중 3개면 정답 |
| 7200RPM·4TB 이상 HDD | 103개 | Q27 은 100행에서 잘림 → 부분집합 비교 |

## 5. 진행 방법

```bash
python tools/nl2sql_eval.py "docs/test/test 3/test_3_questions.json"
```

- 토큰 예상: 생성까지 가는 질문 약 34개 × 1.3회 × 3천 ≈ **13만 토큰**.
- LLM 한도에 걸리면 멈춘다 → `--drop-rate-limited` 후 출력된 명령으로 이어 돌린다.
- 결과: `docs/test/test 3/runs/<실행 시각>/report.md` 의 **"쿼리 품질"** 섹션에 통과한 SQL 이 모두 펼쳐져 있다.
