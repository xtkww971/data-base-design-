# 0003: 처리할 수 없는 질문 판단에 Jev 사용
작성일자: 2026-10-26

작성자: 이도현
## 상태
Proposed (한국어 판정 정확도 PoC 후 Accepted 여부 결정)
## 컨텍스트
현재 NL2SQL 그래프는 `schema_retriever → example_retriever → query_generator → validator` 순서로 동작하고, 검증에 실패하면 최대 3회까지 재생성한다. 이 구조에서 **DB로 답할 수 없는 질문**이 들어오면 다음 문제가 생긴다.

- **판단하는 단계가 없다**: validator는 문법과 `EXPLAIN` 통과 여부만 본다. "오늘 날씨 어때?", "가장 많이 팔린 상품은?"(판매 테이블 없음)처럼 범위 밖의 질문도 무조건 SQL 생성으로 넘어간다.
- **그럴듯한 오답이 더 위험하다**: 프롬프트 규칙 5("스키마 정보가 부족하더라도 예시 쿼리문을 참고하여 쿼리를 생성하세요") 때문에 LLM은 억지로라도 SQL을 만든다. 이 SQL이 `EXPLAIN`을 통과하면 질문과 상관없는 결과가 정상 응답처럼 프론트에 나간다.
- **불필요한 LLM 호출**: 답할 수 없는 질문도 재시도 3회를 모두 쓰고 나서야 실패한다(질문 1건당 최대 3회 생성 호출, 회당 수 초).
- **LLM의 거절 사유가 버려진다**: `query_generator`는 `SQLGenerationResult.error`로 생성 불가 사유를 받지만 반환할 때 `"error": ""`로 덮어쓴다.
- **추천 견적 요청**: 프론트 추천 견적 페이지의 기본 질문은 "300만원 안팎의 예산으로 컴퓨터 견적 맞춰줘"이다. 이것은 SQL 한 번으로 답할 수 있는 조회가 아니라 부품 조합과 호환성 판단이 필요한 요청인데, 지금은 단순 조회와 구분하지 못한다.

Jev를 이용해서 질문의 처리 가능성 판단을 맞기면 답할 수 없는 질문에 대한 처리를 할 수 있지 않을까?

## 결정
SQL 생성 전에 질문이 처리 가능한지 판정하는 `answerability_judge` 노드를 LangGraph 그래프에 추가하고, 판정 모델로 **TypeSafe의 Jev**(`jev-latest`)를 사용한다.

### Jev 개요
- 텍스트를 생성하지 않고, 입력(`state`)에 대한 **타입이 정해진 판정**을 돌려주는 "System One" 모델이다.
- 질문 유형은 `choice`(선택지 중 하나), `score`(루브릭 점수), `noul`(참일 확률 0~1) 세 가지다. 한 요청에 여러 질문을 넣으면 병렬로 평가된다.
- `choice` 응답에는 선택 결과와 함께 선택지별 `probabilities`, 확률이 얼마나 한쪽으로 몰렸는지를 나타내는 `confidence`(0~1)가 포함된다.
- 호출 방식: `POST https://api.typesafe.ai/v1/systemone`, `Authorization: Bearer <API_KEY>`. Python SDK는 `typesafe-sdk`(Python 3.10 이상)이다.
- 공개 수치(TypeSafe 사이트 기준, 자체 측정): 입력 10억 토큰당 $42, 예시 워크플로 기준 LLM 8.5초 대비 0.11초.

### 그래프 배치
- **위치**: `schema_retriever` 다음, `example_retriever` 이전. 어떤 테이블이 있는지 알아야 판단할 수 있으므로 검색된 스키마를 `state`에 함께 넣는다.
- **질문 정의**:
  ```python
  questions = {
      "verdict": Choice(
          instructions="PC 부품 쇼핑몰 DB에 대한 SQL 조회 한 번으로 이 사용자 질문에 답할 수 있는지 판단",
          criteria={
              "answerable": "제공된 스키마의 테이블/컬럼으로 조회해 답할 수 있음",
              "out_of_scope": "PC 부품·쇼핑몰과 무관한 질문",
              "missing_data": "주제는 맞지만 판매량·리뷰 등 스키마에 없는 데이터가 필요함",
              "ambiguous": "조건이 모호해 하나의 SQL로 확정할 수 없음",
              "recommendation": "예산에 맞춘 견적 조합 등 여러 부품을 골라 조합해야 하는 요청",
          },
      ),
  }
  state = {"question": question, "schema": schema_info}
  ```
- **분기 규칙**:
  | 판정 | 처리 |
  |---|---|
  | `answerable` | 다음 노드로 진행 |
  | 그 외 판정 + `confidence ≥ 0.7` | 바로 `END`. `verdict`를 응답에 담는다 |
  | 그 외 판정 + `confidence < 0.7` | 확신이 낮으므로 거절하지 않고 생성 단계로 진행 |
  | Jev 호출 실패·타임아웃(1초) | 판정 없이 생성 단계로 진행 (fail-open) |

  거절할 때만 높은 확신을 요구해 오거절을 줄인다. 0.7은 시작값이고 PoC 결과로 조정한다.
- **사유 문구**: Jev는 이유 문장을 생성하지 않는다. 사용자에게 보여 줄 안내 문구는 판정별로 고정한다. 예: `missing_data` → "판매·리뷰 정보는 아직 제공하지 않아요."
- **응답 계약**: nl2sql `QueryResponse`에 `verdict`, `confidence` 필드를 추가한다. 백엔드는 `answerable`이 아니면 SQL을 실행하지 않고 `NL2SQL_UNANSWERABLE` 에러 코드와 판정별 문구를 프론트에 전달한다.
- **설정**: 루트 `.env`에 `TYPESAFE_API_KEY`를 추가하고 docker compose `nl2sql` 서비스 환경 변수로 넘긴다. 키가 없으면 Judge 노드를 건너뛰어 팀원 로컬 환경이 깨지지 않게 한다.
- **선행 수정**: Jev와 별개로 `query_generator`가 `result.error`를 버리지 않게 고친다. 값이 있으면 재시도하지 않고 종료한다.

## 근거
- **문제 유형과 일치**: 처리 가능 여부는 고정된 5개 선택지 분류다. Jev의 `choice`는 이 형태 그대로 결과를 돌려주므로 JSON 파싱 실패나 형식 이탈이 없다.
- **확신도 기반 분기**: LLM 판정은 "맞다/아니다"만 주고 얼마나 확실한지 알기 어렵다. Jev는 `confidence`를 함께 주므로 "확실할 때만 거절"이라는 정책을 코드로 표현할 수 있다. 오거절이 가장 큰 위험인 이 기능에서 핵심 장점이다.
- **지연과 비용**: 답할 수 있는 질문은 호출이 1회 늘지만, 공개 수치대로라면 0.1초 수준이라 체감되지 않는다. 비용도 무시할 수준이다. 반면 답할 수 없는 질문은 수 초짜리 LLM 생성 호출 최대 3회를 아낀다.
- **LangGraph 구조와 잘 맞음**: 노드 1개와 `add_conditional_edges` 1개로 붙고, LangSmith에서 판정 결과와 확신도도 함께 추적된다(ADR 0001).
- **생성 모델과 분리된 판정자**: 같은 Groq 모델이 판정까지 하면 생성할 때와 같은 방향으로 틀리기 쉽다. 다른 종류의 모델이 판정하면 그 상관이 줄어든다.

## 대안
- **Groq LLM으로 Judge 노드 구현**: 키를 새로 받을 필요가 없고 이유 문장도 생성할 수 있다. 하지만 호출당 수 초가 걸리고, 확신도가 없어 오거절 제어가 어렵고, 생성기와 같은 모델이라 판정이 독립적이지 않다. **Jev PoC가 한국어에서 기대 이하일 때의 차선책**으로 둔다.
- **생성기에 거절을 맡기기(선행 수정만 적용)**: 추가 호출이 없지만, "SQL을 만들어라"와 "못 하면 거절해라"가 한 프롬프트에서 충돌하고 규칙 5 때문에 생성 쪽으로 기운다. 선행 수정으로만 적용한다.
- **벡터 검색 유사도 임계값**: LLM 호출이 없지만, 테이블이 11개뿐이라 어떤 질문이든 무언가 검색되므로 `missing_data`나 `ambiguous`를 구분하지 못한다.
- **키워드/규칙 기반 필터**: 빠르고 결정적이지만 한국어 표현이 다양해 규칙 유지 비용이 크다.

## 결과
- 범위 밖 질문과 데이터 부족 질문이 SQL 생성 전에 걸러지고, 사용자에게 판정별 안내가 전달된다.
- 외부 서비스 의존성과 API 키가 하나 늘어난다. 장애 시 fail-open이라 Judge가 없는 현재 동작으로 돌아갈 뿐, 기능이 멈추지는 않는다.
- 사용자 질문과 검색된 스키마 설명이 TypeSafe로 전송된다. 개인정보는 포함되지 않지만, 팀 차원에서 외부 전송을 허용하는지 확인한다.
- **확인되지 않은 부분**: TypeSafe 문서에는 지원 언어가 명시돼 있지 않다. Accepted 전에 다음 PoC를 진행한다.
  1. `few_shot_examples.json`의 질문(정답 `answerable`)에 거절 대상 질문 20~30개(판정별 4~6개)를 더해 평가 세트를 만든다.
  2. Jev와 Groq Judge를 같은 세트로 돌려 정확도, **오거절률**, 지연을 비교한다.
  3. Jev가 오거절률이 낮고 정확도가 Groq와 비슷하거나 높으면 채택하고, `confidence` 임계값을 결과에 맞춰 정한다.
- 판정 기준이 `criteria` 설명에 들어가므로 스키마(`schema_docs.json`)가 바뀔 때 함께 확인해야 한다.
- **보안 경계가 아님**: Judge는 사용성 개선 장치일 뿐이다. 현재 `schema_docs.json`에 `users` 테이블이 들어 있어 질문으로 회원 정보를 조회할 수 있다. 이건 스키마 문서에서 제외하거나 nl2sql 전용 DB 계정 권한으로 막아야 한다.
